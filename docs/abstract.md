# Abstract Domain Model

Этот документ описывает проект на абстрактном уровне: какие в нем есть сущности, как они ведут себя во времени, и что важно учитывать при разработке фронтенда.

Документ намеренно смотрит на систему глазами клиента и продуктовой логики, а не только базы данных.

## Общая картина

Проект представляет собой backend для игровой учетной записи и связанных игровых систем. В нем есть несколько крупных доменов:

- аутентификация пользователя через Discord и выпуск JWT;
- профиль пользователя и его состояние;
- сквады и инвайты;
- ограничения на действия пользователя;
- каталог игровых сущностей;
- владение игровыми сущностями;
- кошелек для валют;
- скины;
- административное управление;
- аудит и журналы изменений.

На практике фронтенд должен воспринимать backend не как набор независимых таблиц, а как несколько пересекающихся слоев:

- identity layer: кто пользователь и авторизован ли он;
- social layer: состоит ли он в скваде, есть ли инвайты, есть ли ограничения;
- economy layer: чем он владеет, какие у него балансы, что активировано, что истекло;
- admin layer: какие сущности видит и чем может управлять администратор;
- media/config layer: мета-конфиги и бинарные ресурсы вроде скинов и изображений.

## 1. User

`User` — центральная сущность системы.

### Что описывает

Пользователь хранит:

- внутренний `id` как UUID;
- внешний `discord_id`;
- отображаемое имя `username`;
- `avatar_url`;
- `email`;
- `auth_epoch`;
- флаги `is_active` и `is_superuser`;
- текущий `squad_id`, если пользователь состоит в скваде;
- `deactivation_reason`;
- служебные даты `last_login_at` и `created_at`.

### Особенности поведения

- Пользователь либо создается при первом успешном Discord-входе, либо обновляется при повторном входе.
- При входе username из Discord используется только если он проходит локальную валидацию и не занят. Иначе сервер генерирует новый ник.
- `auth_epoch` используется как механизм отзыва токенов. Если админ сбрасывает epoch, старые JWT становятся недействительными.
- `is_active = false` означает, что пользователь существует, но не может использовать обычные protected endpoints.
- `is_superuser = true` открывает административные маршруты.
- `squad_id` отражает факт членства, но не заменяет саму сущность `Squad`.

### Что важно фронтенду

- Пользователь и его авторизация не одно и то же. Даже если на клиенте есть token, `/api/auth/verify` и protected endpoints могут ответить ошибкой, если пользователь деактивирован или токен уже отозван через `auth_epoch`.
- `username` не должен считаться immutable.
- `squad_id` на клиенте лучше трактовать как hint. Полноценные данные о скваде нужно брать через squad endpoints.
- UI должен быть готов к состоянию “пользователь существует, но недоступен для входа”.

### Рекомендации для фронтенда

- Держать отдельный auth state и отдельный current-user state.
- При любом `403` на protected endpoints уметь переводить приложение в состояние “нужно переавторизоваться”.
- Не строить критическую логику только на данных из JWT; источник истины для UI — ответы API.

## 2. Auth Session / AuthRay

`AuthRay` — временная сущность авторизационного челленджа.

### Что описывает

Она хранит:

- идентификатор записи;
- `pow_prefix`;
- `pow_complexity`;
- способ доставки результата авторизации;
- цель доставки;
- время создания.

### Особенности поведения

- Это одноразовый auth challenge.
- После успешной или неуспешной попытки `authorize` запись удаляется.
- Поддерживаются два режима завершения auth flow:
  - `redirect`;
  - `polling`.
- В polling-режиме фактический результат живет не только в БД, но и во временном runtime-кеше.

### Что важно фронтенду

- Auth flow двухстадийный:
  - `prepare`;
  - затем `authorize`.
- В polling flow нужно уметь долго ждать статус и повторять запросы на poll endpoint.
- Poll endpoint не гарантирует мгновенный результат, поэтому UX должен уметь жить в состоянии `pending`.

### Рекомендации для фронтенда

- Оборачивать auth flow в state machine, а не в один “submit”.
- Для polling:
  - хранить `poll_id` локально;
  - предусмотреть timeout/retry UX;
  - корректно обрабатывать статусы `pending`, `success`, `error`, `expired`.
- Не считать, что authorize всегда вернет финальный usable access token прямо для UI-редиректа; это зависит от delivery mode.

## 3. Auth Poll Result

Это не отдельная таблица, а runtime-сущность.

### Что описывает

Состояние polling-авторизации:

- `pending`;
- `success`;
- `error`;
- `expired`.

### Особенности поведения

- Успешный или ошибочный результат кешируется на ограниченное время.
- Polling — это фактически long-poll.
- Если событие пропущено подписчиком, сервер пытается отдать cached result.

### Что важно фронтенду

- Polling response — это не просто boolean.
- `success` приносит и токен, и user snapshot.
- `error` — часть нормального flow, а не только “сервер умер”.

### Рекомендации для фронтенда

- Отрисовывать auth statuses явно.
- Не превращать любой не-`success` в generic error page.

## 4. Restriction

`UserRestriction` — ограничение на конкретные действия пользователя.

### Что описывает

Хранит:

- внутренний `id`;
- `user_id`;
- `restriction_key`;
- `reason`;
- `created_at`.

Сейчас в системе есть два ключа:

- `create_squad`;
- `join_squad`.

### Особенности поведения

- Ограничение — это бинарный флаг на возможность действия.
- Ограничения независимы друг от друга.
- Пользователь может быть активным, но при этом иметь ограничения.
- Ограничения отдаются и в self-view, и в admin-view.
- Для UI есть отдельный meta endpoint с локализуемым описанием ограничений.

### Что важно фронтенду

- Ограничения не заменяют role system. Это тонкие продуктовые запреты.
- Нельзя вычислять readable label по ключу на клиенте “на глаз”; лучше использовать `/api/meta/restrictions`.
- Ограничения влияют на UX действий, а не на общую авторизацию.

### Рекомендации для фронтенда

- Загружать restriction meta один раз и кэшировать.
- Строить UX не только на ошибках серверных мутаций, но и на предварительном отключении недоступных действий.
- Но даже при disabled UI оставлять сервер главным источником истины: race conditions и админские изменения возможны.

## 5. Squad

`Squad` — постоянная социальная группа пользователей.

### Что описывает

Сущность хранит:

- `id`;
- `leader_user_id`;
- `name`;
- `image_key` и `image_content_type`;
- `is_restricted`;
- `restriction_reason`;
- `created_at`, `updated_at`.

### Особенности поведения

- У сквада всегда один лидер.
- Членство пользователя в скваде фактически хранится в `User.squad_id`.
- Сквад может быть restricted. Это отдельное состояние модерации.
- Restricted squad продолжает существовать, но часть пользовательских действий запрещается.
- Лидер не может “выйти” из сквада; он должен удалить сквад.
- Удаление сквада очищает membership у всех участников и удаляет invite-ы.

### Что важно фронтенду

- Сквад — это не просто список участников. У него есть собственный lifecycle:
  - создание;
  - обычное существование;
  - ограничение админом;
  - снятие ограничения;
  - удаление.
- `is_restricted` должен считаться важным продуктовым состоянием и явно отражаться в UI.
- Даже если пользователь состоит в скваде, это не гарантирует, что ему доступны rename/invite/kick/image actions.

### Рекомендации для фронтенда

- Отображать squad restriction как заметное состояние, а не как скрытую ошибку из мутации.
- Разделять UI для:
  - обычного участника;
  - лидера;
  - админа.
- Не хранить image URL навсегда. Лучше использовать URL из API как текущий runtime view.

## 6. Squad Invite

`SquadInvite` — временное приглашение пользователя в сквад.

### Что описывает

Хранит:

- `id`;
- `squad_id`;
- `inviter_user_id`;
- `invited_user_id`;
- `expires_at`;
- `created_at`.

### Особенности поведения

- Invite адресован конкретному пользователю.
- Invite имеет TTL.
- Истекшие invite-ы отфильтровываются из пользовательских списков и могут удаляться в ходе операций.
- Принятие invite-а переносит пользователя в сквад.
- Повторное создание того же активного invite может вернуть уже существующий invite, а не создать дубликат.

### Что важно фронтенду

- Invite — временная сущность. Не стоит считать, что показанный пользователю invite еще существует через минуту.
- UI списка инвайтов всегда должен быть готов к исчезновению invite между refresh и action.
- Принятие invite-а может провалиться не только из-за самого invite, но и из-за:
  - squad restriction;
  - full squad;
  - user restriction `join_squad`;
  - того, что пользователь уже успел вступить куда-то еще.

### Рекомендации для фронтенда

- В списке инвайтов отображать время истечения.
- Перед accept/decline закладывать optimistic disabled state кнопок.
- После любой invite mutation делать refetch текущего сквада и списка инвайтов.

## 7. Asset Definition

`AssetDefinition` — каталог всех игровых сущностей, которыми потенциально можно владеть.

### Что описывает

Хранит:

- `id`;
- `key`;
- `display_name`;
- `description`;
- `asset_kind`;
- `ownership_model`;
- `is_currency`;
- `is_user_purchasable`;
- `is_public`;
- `is_active`;
- `metadata`;
- `created_at`, `updated_at`.

### Особенности поведения

- `key` — стабильный системный идентификатор для клиента и API.
- Ключ URL-safe и строго lowercase.
- Каталог имеет admin-view и public-view.
- Public-view скрывает не-public и inactive assets.
- `asset_kind` описывает смысл сущности.
- `ownership_model` описывает форму владения.
- Валюта выделена флагом `is_currency`, но при этом обязана быть `Stackable`.

### Что важно фронтенду

- `asset_kind` и `ownership_model` нельзя смешивать:
  - одно отвечает на вопрос “что это”;
  - второе на вопрос “как этим владеют”.
- `metadata` — расширяемое поле. Фронтенд не должен жестко падать из-за новых ключей.
- `is_user_purchasable` не означает, что asset уже есть у пользователя; это свойство каталога, а не инвентаря.

### Рекомендации для фронтенда

- Использовать `key` как основной stable identifier в UI-коде.
- Делать UI rendering extensible через `metadata`.
- Не захардкодивать публичность asset-ов; public catalog уже отфильтрован сервером.

## 8. Ownership: Stackable

`UserStackableAsset` — количественное владение не-валютной сущностью.

### Что описывает

Хранит:

- `user_id`;
- `asset_definition_id`;
- `amount`;
- `updated_at`.

### Особенности поведения

- Запись с amount `0` не хранится как “мертвый остаток”; при переходе к нулю она удаляется.
- Для клиента “существует” только amount > 0.
- Это не используется для валют.
- Изменение количества всегда сопровождается записью в `InventoryOperation`.

### Что важно фронтенду

- Отсутствие записи и нулевое количество для UI эквивалентны.
- Нельзя рассчитывать на то, что asset с amount `0` вернется в списке stackables.

### Рекомендации для фронтенда

- Представлять stackables как sparse collection.
- Любую агрегацию “всех возможных stackables” строить поверх каталога asset-ов, а не только инвентаря.

## 9. Ownership: Entitlement

`UserEntitlement` — бинарное владение не-валютной сущностью.

### Что описывает

Хранит:

- `user_id`;
- `asset_definition_id`;
- `granted_at`;
- `granted_by_actor`;
- `updated_at`.

### Особенности поведения

- Либо есть, либо нет.
- Повторный grant работает идемпотентно.
- revoke удаляет запись целиком.
- История идет не из самой записи, а из `InventoryOperation`.

### Что важно фронтенду

- Entitlement следует считать boolean capability / unlock state.
- `updated_at` не надо путать с “изменением свойств”. Это скорее системный timestamp состояния.

### Рекомендации для фронтенда

- Для entitlement UI удобнее всего делать lookup map по `asset_key`.
- Для магазина или профиля полезно разделять “можно купить” и “уже есть”.

## 10. Ownership: Expirable

`UserExpirableAsset` — временное владение не-валютной сущностью.

### Что описывает

Хранит:

- `user_id`;
- `asset_definition_id`;
- `expires_at`;
- `granted_at`;
- `last_extended_at`;
- `granted_by_actor`;
- `updated_at`.

### Особенности поведения

- Сущность может физически существовать в БД, но логически быть неактивной, если `expires_at <= now`.
- В пользовательском inventory истекшие expirable не возвращаются.
- Presence check для expirable считает `exists = true` только если сущность активна сейчас.
- Продление активного expirable идет от текущего `expires_at`.
- Продление уже истекшего expirable идет от `now`, а не от старого `expires_at`.
- `set_expiration` может как создать новую запись, так и изменить существующую.
- `revoke` удаляет запись целиком.

### Что важно фронтенду

- Expirable — это сущность с временной логикой, а не просто дата на карточке.
- Наличие записи в прошлом не гарантирует присутствие в текущем inventory response.
- Для UX подписок и аренды важно уметь показывать:
  - активна сейчас;
  - истекает тогда-то;
  - продление после истечения стартует заново.

### Рекомендации для фронтенда

- Все сравнения активности делать по серверному `expires_at`, а не по предположениям клиента.
- После пролонгации всегда refetch-ить сущность, а не вычислять локально новый expiry.
- Если UI показывает архив или историю, брать это из operation history, а не надеяться найти expired asset в inventory.

## 11. Inventory Operation

`InventoryOperation` — append-only журнал изменений обычного инвентаря.

### Что описывает

Фиксирует:

- пользователя;
- asset definition;
- ownership model;
- тип операции;
- actor;
- изменение количества;
- изменение срока действия;
- причину;
- metadata;
- время.

### Особенности поведения

- Это источник истории, а не текущего состояния.
- Используется для stackable, entitlement и expirable.
- Хранит actor model:
  - `system`;
  - `user`;
  - `admin`.
- Для expirable хранит previous/new expiration.

### Что важно фронтенду

- Operation history лучше показывать как timeline событий, а не как snapshot-инвентарь.
- Формат operation_type лучше считать расширяемым.

### Рекомендации для фронтенда

- Не жестко связывать UI только с текущим списком operation_type. Лучше использовать fallback-рендер “unknown operation”.
- Причину операции стоит показывать как необязательную информацию, а не как всегда присутствующее поле.

## 12. Wallet Balance

`WalletBalance` — текущий баланс валюты пользователя.

### Что описывает

Хранит:

- `user_id`;
- `currency_asset_definition_id`;
- `balance`;
- `updated_at`.

### Особенности поведения

- Wallet существует отдельно от inventory.
- Даже если строки баланса еще нет, API может вернуть баланс `0` для существующей валюты.
- Валюта обязана быть asset с `is_currency = true`.
- Баланс не должен становиться отрицательным.

### Что важно фронтенду

- “Нет записи” и “нулевой баланс” для UI часто следует считать одинаковым состоянием.
- Валюты не нужно искать в inventory stackables.

### Рекомендации для фронтенда

- Строить все currency widgets только на wallet endpoints.
- Для неоткрытых еще кошельков спокойно отображать `0`, если такой ответ отдает API.

## 13. Wallet Transaction

`WalletTransaction` — append-only журнал изменения валютного баланса.

### Что описывает

Хранит:

- пользователя;
- валюту;
- тип операции;
- actor;
- `delta`;
- `balance_after`;
- причину;
- metadata;
- время.

### Особенности поведения

- Это основной audit trail для валют.
- Поддерживаются операции:
  - credit;
  - debit;
  - adjustment.
- История отделена от текущего balance.

### Что важно фронтенду

- `delta` может быть положительным и отрицательным.
- Для истории кошелька лучше показывать both:
  - изменение;
  - итоговый баланс после операции.

### Рекомендации для фронтенда

- Форматировать transaction list как банковскую ленту.
- Отрицательные и положительные операции визуально различать.
- Не пытаться локально пересчитывать balance из transactions как единственный источник истины; для текущего состояния есть balance endpoint.

## 14. Audit Log

`AuditLog` — общий административный и системный журнал действий высокого уровня.

### Что описывает

Хранит:

- `action`;
- `actor_user_id`;
- `target_user_id`;
- `reason`;
- `metadata`;
- `created_at`.

### Особенности поведения

- Это не то же самое, что inventory history или wallet history.
- Журнал используется для крупных административных и системных действий:
  - регистрация пользователя;
  - изменение профиля админом;
  - деактивация;
  - управление superuser;
  - модерация сквадов;
  - ограничения и т.д.

### Что важно фронтенду

- Это скорее admin/investigation сущность.
- Если позже будет UI журнала, его стоит показывать отдельно от игровой экономики.

### Рекомендации для фронтенда

- Не смешивать audit log и product activity feed.
- Для action names предусмотреть словарь отображения, а не печатать raw action как финальный текст.

## 15. Skin

Скин — это пользовательский бинарный ресурс, а не отдельная таблица.

### Что описывает

Система хранит skin в object storage и оперирует:

- UUID пользователя;
- моделью скина `default` или `slim`;
- PNG-файлом с валидацией.

### Особенности поведения

- Загрузка принимает multipart/form-data.
- Разрешен только PNG.
- Есть ограничения на размер и корректность файла.
- Получение скина — это binary response `image/png`.
- Совместимый GamerVii flow предполагает `IsSlim`, но сейчас сервер отвечает `false`.

### Что важно фронтенду

- Skin API отличается от JSON endpoints.
- Ошибки skin upload имеют свой набор error code/message.
- Скин может отсутствовать, и это нормальное состояние.

### Рекомендации для фронтенда

- Для upload делать отдельный transport/path, не универсализировать под обычные JSON мутации.
- Для preview использовать optimistic local preview еще до upload.
- Для чтения skin учитывать `404` как “скин не установлен”.

## 16. Compatibility Auth View

`/api/compat/gamervii/auth` возвращает совместимый ответ для внешнего клиента.

### Особенности поведения

- В отличие от обычного API, ошибки кодируются внутри body как часть совместимого формата.
- `Login` ожидает UUID пользователя.
- `Password` ожидает JWT.

### Что важно фронтенду

- Это endpoint не для обычного first-party UI.
- Если используется, его нельзя обрабатывать по тем же предположениям, что обычные REST JSON endpoints с четкими status code semantics.

## 17. Meta Config

Meta endpoints не описывают пользовательское состояние, а отдают клиенту справочные данные.

### Что в них лежит

- словарь ограничений и их локализованные описания;
- конфиг сквадов:
  - лимит участников;
  - TTL invite;
  - правила имени;
  - лимиты изображения.

### Особенности поведения

- Это хорошие кандидаты на агрессивный cache.
- Это источник UI-валидации, но не замена backend-валидации.

### Рекомендации для фронтенда

- Загружать на старте приложения или при инициализации соответствующих экранов.
- Использовать для:
  - helper text;
  - client-side validation;
  - ограничений file picker;
  - локализованных описаний.

## 18. Admin Views

Административный слой не вводит принципиально новые игровые сущности, но открывает расширенные представления и мутации существующих сущностей.

### Что это значит абстрактно

- admin может видеть inactive и non-public assets;
- admin может управлять чужим инвентарем и кошельком;
- admin может включать и снимать restrictions;
- admin может модерировать сквады;
- admin может деактивировать пользователей и отзывать их токены через auth epoch.

### Что важно фронтенду

- Admin UI почти всегда должен показывать больше информации, чем user UI.
- Idempotent operations нужно отображать спокойно:
  - повторный grant entitlement;
  - повторное restriction grant;
  - delete image при отсутствии image.

### Рекомендации для фронтенда

- Делать admin UI “state-reconciling”, а не “optimistic forever”.
- После admin mutations чаще выгоднее refetch-ить сущность и историю, чем пытаться локально пересобирать все derived state.

## Ключевые поведенческие принципы системы

Ниже короткий список принципов, которые особенно важны для фронтенда.

### 1. Много временных сущностей

В проекте много сущностей, чье существование зависит от времени:

- auth challenge;
- polling result;
- squad invite;
- expirable asset.

Фронтенд не должен считать любой полученный объект “стабильным до следующего reload”.

### 2. Много логически бинарных, но физически удаляемых состояний

Некоторые состояния исчезают из выдачи полностью, а не возвращаются как “нулевые”:

- stackable с `amount = 0`;
- revoked entitlement;
- revoked expirable;
- expired expirable в обычном inventory response;
- просроченные invites в пользовательском списке.

Это значит, что для фронтенда важен паттерн “отсутствие объекта тоже состояние”.

### 3. Каталог и владение разделены

`AssetDefinition` отвечает на вопрос “что в принципе существует”, а inventory/wallet — “чем владеет конкретный пользователь”.

UI магазина, профиля, витрины и инвентаря должен учитывать оба слоя.

### 4. История и текущее состояние разделены

Есть отдельные журналы:

- `InventoryOperation`;
- `WalletTransaction`;
- `AuditLog`.

Их нельзя заменять текущими snapshot endpoint-ами.

### 5. Сервер активно использует идемпотентность

Некоторые операции безопасно повторять:

- grant entitlement;
- grant restriction;
- delete/revoke некоторых сущностей, если их уже нет.

Это упрощает retry logic на фронте.

## Практические рекомендации для frontend architecture

### 1. Разделить клиентские модели

Рекомендуется держать отдельно:

- `CurrentUser`;
- `AuthState`;
- `RestrictionDictionary`;
- `MySquad`;
- `MyInvites`;
- `AssetCatalog`;
- `Inventory`;
- `Wallet`;
- `Admin*` сущности.

Не сводить все в один giant store.

### 2. Использовать сервер как источник истины для derived state

Особенно для:

- squad membership;
- invite availability;
- expirable activity;
- wallet balance;
- public/admin visibility asset-ов.

### 3. Явно моделировать empty states

Нужны отдельные UI-состояния:

- нет сквада;
- нет инвайтов;
- нет активных expirables;
- пустой кошелек;
- entitlement отсутствует;
- скин не установлен.

### 4. Разделять ошибки по смыслу

В проекте есть несколько типов отказов:

- `401`: нет авторизации;
- `403`: есть авторизация, но действие запрещено или токен/пользователь invalid in current state;
- `404`: сущность исчезла или не существует;
- `422`: бизнес-ошибка формата “недостаточно баланса/количества”;
- compatibility endpoints могут кодировать ошибку в body.

UI должен трактовать их по-разному.

### 5. Рефетч после мутаций важнее локальной магии

Особенно после:

- squad actions;
- invite actions;
- admin mutations;
- prolong/set expiration;
- wallet mutations.

Причина: много скрытых side effects и derived state.

### 6. Осторожно работать со временем

Для expirable и invite UX:

- отображать server timestamps;
- не полагаться только на локальные таймеры;
- быть готовым, что сервер уже считает объект истекшим.

### 7. Делать UI расширяемым

Наборы enum-ов и operation types со временем могут расширяться:

- `AssetKind`;
- `OwnershipModel`;
- restriction keys;
- operation types;
- audit actions.

Клиент не должен ломаться на новых значениях.

## Рекомендуемый взгляд фронтенда на систему

Если сильно упростить, фронтенду стоит видеть систему так:

- Пользователь — это аккаунт и права доступа.
- Сквад — это текущее социальное состояние пользователя.
- Ограничения — это product-level блокировки отдельных действий.
- Asset catalog — это словарь игровых сущностей.
- Inventory — это не-валютное владение игрока.
- Wallet — это валютное владение игрока.
- Histories — это отдельные ленты событий, а не текущий state.
- Admin layer — это отдельный режим интерфейса, а не просто “те же экраны, но с extra buttons”.

Именно такая модель лучше всего соответствует реальному поведению backend-а и позволит фронтенду быть устойчивым к race conditions, истечению сущностей и будущему расширению домена.
